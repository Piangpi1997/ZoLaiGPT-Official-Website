Track source code by release and commit

Give a teammate enough information to find the exact source you used, rebuild it and investigate what changed.

Record both the release and the commit

Start from the publisher’s release page. Record the repository, the release tag and the full commit SHA behind the tag. A branch such as main advances over time, so a link to that branch can show different code to the next reader. A tag gives people a recognizable release name. A commit SHA pins the snapshot even if that tag is later moved.

If you already cloned the repository, run these commands from the project directory. Substitute the publisher’s actual tag for v1.2.0. Compare the two commit IDs before saying that your checkout matches the release.

git rev-parse HEAD
git rev-parse 'v1.2.0^{commit}'
git status --short

If the command for the tag fails, fetch the tags from the official repository and try again. Record local edits or untracked files before building, since they can change the result without changing the commit ID.

Keep a source record with the build

  • Source: repository URL, release tag, full commit SHA and, if used, the source archive filename.
  • Integrity: the archive’s SHA-256, where you obtained the expected value and the date you verified it. Keep the APK checksum in a separate field.
  • Build: the target, exact build command, JDK, Android SDK and dependency lockfiles, plus any local patches. Record required environment variable names without recording credentials.

Compare versions before opening a bug report

If a build fails on a new release, rerun the same command with the same tools against the last working commit. Include both commit IDs, the first relevant error and the steps to reproduce it. A commit match identifies the source snapshot. Reproducing identical APK bytes can additionally require the same signing configuration and a reproducible build process.
